# 03 - 架构设计

> 状态：方向性设计 v2 · 2026-10-26（技术栈由 Tauri 2 改为 Electron + TypeScript，选型依据见 [ADR 0001](adr/0001-采用Electron与macOS优先.md)）

## 1. 总体架构

```
┌─────────────────────────────────────────────────────────┐
│                      BaiZe 桌面进程                        │
│                                                           │
│  ┌───────────┐   事件总线 (Event Bus)   ┌──────────────┐  │
│  │  感知层    │ ───────────────────────▶ │   行为系统    │  │
│  │ agent hooks│   （系统事件/用户交互/    │ 效用选择器    │  │
│  │ 系统事件    │     渠道消息/定时器）     │ 情绪状态机    │  │
│  │ 输入监听    │                          └──────┬───────┘  │
│  └───────────┘                                 │ 动作指令   │
│                                                 ▼          │
│  ┌───────────┐   统一通道接口            ┌──────────────┐  │
│  │  渠道适配器 │ ◀─────────────────────▶ │   决策层      │  │
│  │ TG/飞书/QQ │   （文本/语音/图片）      │ 规则引擎(95%) │  │
│  │ 企微/本地UI │                          │ LLM(低频/对话)│  │
│  └───────────┘                          └──────┬───────┘  │
│                                                 │           │
│  ┌───────────┐   执行通道抽象            ┌──────▼───────┐  │
│  │  执行层    │ ◀────────────────────── │  记忆引擎     │  │
│  │ 通知/语音  │                         │ 四层记忆      │  │
│  │ IPC/UIA   │                         │ 遗忘/整理     │  │
│  └───────────┘                         └──────────────┘  │
└─────────────────────────────────────────────────────────┘
```

核心思想（源自产品定义）：**桌宠是个人 Agent 的脸**。感知 → 行为/决策 → 执行全部解耦，桌宠 UI 只是执行层的一个"脸面"通道，Telegram bot 是另一个通道，二者共享同一颗大脑。

## 2. 技术栈选型（建议，骨架负责人可复核）

| 层 | 选型 | 理由 |
|---|---|---|
| 应用框架 | **Electron + TypeScript**（electron-builder 打包） | 自带 Chromium，Mac / Windows 渲染一致；clawd-on-desk、dsh-pet 已验证透明置顶 + 鼠标穿透的桌宠窗口；全栈一门语言，贡献门槛最低。代价是常驻内存约 150-250MB，靠隐藏时暂停渲染、模型按需加载缓解 |
| 渲染层 | Web（React/Vue + Canvas），`<video>` 播放 VP9-Alpha webm，序列帧兜底 | Chromium 在 Mac 上也支持 VP9 透明视频，素材链一套格式通吃双平台（Tauri 在 Mac 用 WKWebView，不支持） |
| 原生能力 | Electron API（透明窗口、`setIgnoreMouseEvents` 穿透、全局快捷键、通知、托盘）+ 必要时 Node 原生模块；Mac 独有能力（Apple 端侧模型、辅助功能）后续以小型 Swift 辅助进程提供 | 主体不引入第二门语言 |
| 核心逻辑 | 纯 TS 包 `packages/core`（记忆、行为、情绪），不依赖 Electron | 桌面端、bot、测试共用同一颗大脑 |
| 存储 | better-sqlite3 + sqlite-vec（记忆库）；文件系统（角色包、资产） | 单文件、零运维、可导出 / 导入（隐私承诺的技术前提） |
| Embedding | 本地小模型（如 bge-small-zh，经 transformers.js / onnxruntime-node） | 不依赖任何 LLM 供应商，换供应商不影响记忆；更换 embedding 模型时需提供重建索引流程 |
| LLM 接入 | **多供应商聚合**：OpenAI 兼容适配器覆盖 GPT / DeepSeek / GLM / Kimi / MiniMax / 小米 MiMo / Ollama；Anthropic 独立适配器覆盖 Claude；统一能力协商（流式 / 工具调用 / 多模态按供应商声明降级） | 用户想用哪家就用哪家，避免绑定单一供应商 |
| 语音 | **全本地**：sherpa-onnx（Node 包）提供 VAD(silero) + 唤醒词 + ASR(SenseVoice-Small) + TTS(MeloTTS / Kokoro)；麦克风经 Chromium `getUserMedia` 开启回声消除 | 零云费；AEC 现成，barge-in 不会被自己的声音触发；默认全局监听，可切换快捷键触发 |
| IPC/进程 | 主进程 + 渲染进程；bot 网关在主进程内模块化（不必独立进程，从简） | Electron IPC 足够 |
| 构建发布 | pnpm monorepo（`apps/desktop`、`packages/core`、`packages/channels`、`packages/voice`）；GitHub Actions 矩阵构建（macOS arm64 + Windows）→ GitHub Releases | 打 tag 自动出双平台包，本机无需打包环境；第一阶段自签名，更新为"提示 + 跳转下载页" |

## 3. 关键子系统

### 3.1 角色包（Character Pack）

```
my-character/
├── manifest.json        # 名称、人设种子参数、情绪映射、音色配置、版本
├── animations/          # webm(vp9-alpha) / 序列帧，按动作枚举命名
│   ├── idle_breath.webm
│   ├── pet_happy.webm
│   └── ...
├── persona/
│   └── persona.md       # 人设文档（喂给 LLM 的 system prompt 素材）
└── LICENSE.txt          # 资产授权声明（平台强制校验）
```

动作枚举是平台契约（idle / click / drag / throw / speak / angry / sleep / celebrate …），角色包只需覆盖子集，缺失动作回退默认实现。

### 3.2 事件总线与感知层

- 事件源：用户交互（点击/拖拽/语音）、agent hooks（Claude Code / Codex / Cursor，参照 clawd-on-desk 的 hooks 注册方案）、系统事件（通知、电量、时段）、git / CI 事件、渠道消息、定时器。
- 事件 = `{source, type, payload, timestamp}`，行为系统与记忆引擎各自订阅，互不阻塞。

### 3.3 行为系统

- 效用选择器：规则先识别场景、圈出候选；每个候选按 `效用 = f(情绪向量, 时段, 最近事件, 冷却, 重复惩罚)` 打分，再**按分数加权随机抽取**（如 softmax，温度参数外置，可调"性格的随机程度"），同一场景不重样。
- 台词池：LLM 在空闲时按"场景 × 情绪"批量生成台词并缓存在本地，自发行为触发时随机抽取，不实时等待模型；池子耗尽或过期后后台补充。**95% 的动作由规则驱动（零成本、毫秒级）**，LLM 只在低频节点介入（睡前总结、久别重逢、用户点名聊天）。
- 打断优先级：用户拖拽 > 语音对话 > 渠道消息提示 > 自发行为。
- 打分权重外置为配置文件——二开者与高级用户可调性格。

### 3.4 渠道适配器

统一接口（伪码）：

```ts
interface ChannelAdapter {
  start(cfg): Promise<void>;                    // 连接、配对
  onMessage(cb: (msg: InboundMessage) => void): void;
  send(out: OutboundMessage): Promise<void>;    // 自动按平台转码音频/分片
  capabilities(): ChannelCaps;                  // 是否支持语音条/图片/长度限制
}
```

身份归一：桌宠 UI 生成配对码 → 各渠道首次对话输入配对码 → 渠道身份绑定到同一主人档案。

### 3.5 执行层

通道抽象：`Notifier`（系统通知）、`Speaker`（TTS）、`Relay`（agent 传话，官方通道）、`Automation`（UI 代操作，插件化，默认禁用）。执行敏感动作一律走确认队列。

## 4. 安全与隐私模型

1. 记忆数据本地 SQLite，**永不上传**；云端 LLM 调用时仅传输当前对话所需最小上下文（由记忆引擎的检索 budget 决定）。
2. 远程渠道权限模型：默认 `chat`（聊天 + 状态播报）；`approve`（远程批准 agent 操作）与 `act`（触发执行层）为显式开关 + 二次确认。
3. 所有执行层敏感动作进审计日志（本地），可在设置页回放。
4. 客户端不做任何遥测：更新检查只请求 GitHub Releases 公开接口，不携带任何标识；崩溃日志只存本地，由用户自行选择是否附到 issue（见 [05 §5](05-许可证与合规.md)）。

## 5. 开放性承诺（架构层落实）

- 记忆存储 schema 与导出格式（JSON/SQLite 直读）写进公开规范文档。
- 行为打分、情绪参数、动作枚举全部外置可配置。
- 插件 SDK（事件源 / 执行通道 / 渠道适配器三类插件）与角色包规范是公开发布物，不是内部实现细节。
