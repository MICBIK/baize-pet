# 04 - 记忆系统设计

> 状态：核心壁垒的完整设计 · 2026-10-26 · 本模块是全项目最重要的单体设计

## 0. 设计目标

1. **不越用越慢**：检索路径分级，回复永不被记忆检索阻塞。
2. **像人一样记、像人一样忘**：遗忘是特性不是缺陷——"只记得大概"与"想不起来了"都是产品体验的一部分。
3. **永远可导出**：存储格式公开，用户的记忆可直读、可备份、可迁移（隐私承诺的技术前提）。

## 1. 四层记忆

| 层 | 内容 | 规模 | 写入时机 | 读取时机 |
|---|---|---|---|---|
| **工作记忆** | 当前对话窗口 | 固定 N 轮 | 每轮 | 每轮（零检索） |
| **语义记忆** | 蒸馏出的稳定事实："主人喜欢凌晨写代码"、"我叫小X"、人设画像 | 小（数百条级） | 睡眠整理时从情景蒸馏 / 对话中即时抽取 | **每次回复必用（毫秒级）** |
| **情景记忆** | 具体事件，带时间戳 + 标签 + 情绪值 | 随时间增长 | 每个可记忆事件 | **按需检索**，不阻塞回复 |
| **程序性记忆** | 习惯模式："用户 9-18 点勿扰"、"每天 22 点要点名" | 很小 | 模式识别（睡眠整理） | 行为系统决策时 |

**解决"越用越慢"的关键**：回复只查工作记忆 + 语义记忆（两者规模有界，毫秒级）。情景记忆是唯一随时间增长的层，且**只在需要时按需检索**——不是每句话全库扫描。

**慢检索的拟人化包装**：情景记忆异步检索，若命中，下一句自然引用："对了，我想起来了……"。延迟被转化为"回忆"的表演感。

## 2. 情景记忆的结构（标签体系）

用户需求原话："喜怒哀乐的所有事情都像标签一样记录，各种标签组合搜索出特定事件。"

```
EpisodicMemory {
  id, created_at, last_recalled_at,
  event_type:   [对话 | 里程碑 | 起名 | 争吵 | 帮忙 | 捣蛋 | ...],
  emotion_tags: [开心 | 委屈 | 生气 | 思念 | 骄傲 | ...],   // 情绪标签
  topic_tags:   [工作 | 游戏 | 健康 | 家人 | ...],          // 主题标签
  participants, importance: 0-10,       // 情绪强度加权
  content: 原始事件摘要（可为多粒度：事件 → 段落 → 摘要）,
  embedding: 向量索引,
  decay_state: 活跃 | 压缩 | 印象 | 冷存储,
  pinned: bool                          // 用户手动"永不遗忘"
}
```

标签可组合检索（"去年我们赶 deadline + 熬夜 + 争吵"三标签交 & 向量相似）。**标签由睡眠整理阶段的 LLM 归类打上**，对话时只做轻量抽取。

## 3. 遗忘机制（三段退化 + 强化）

退化方向（时间 × 未被回忆）：

```
活跃 ──(30天未回忆)──▶ 压缩 ──(90天未回忆)──▶ 印象 ──(180天)──▶ 冷存储
原内容                只留摘要：            只留标签+情绪值      仅在"梦境"主题
                     "7月我们一起赶过        "好像发生过什么      对话中偶然浮现
                      一个deadline"          开心的事，想不起来了"
```

强化方向（反向同一条曲线，即艾宾浩斯机制）：

- 事件被回忆一次 → `last_recalled_at` 刷新 + importance 微增；被频繁回忆 → **自动升级进语义记忆**（"我们经常聊猫"成为稳定事实）。
- `pinned` 事件（回忆相册手动 pin）永不退化。

**"想不起来"的表达是设计出来的**：桌宠可以说"我们是不是…发生过什么开心的事？我记不清了"——然后用户的回应本身构成新事件（重新唤起或一起笑忘），这是极强的拟人化交互素材。

## 4. 睡眠整理（Consolidation）

触发：空闲时段（深夜 / 用户挂机超过阈值）+ 待处理事件量。

流水线（后台执行，白天检索零负担）：

1. 聚类当日事件 → 打标签、合并重复、计算 importance；
2. 高频共现的事实 → 蒸馏写/更新语义记忆；
3. 识别周期模式 → 写程序性记忆（供行为系统用）；
4. 执行遗忘退化流转；
5. 更新自我画像与主人画像（画像页数据源）。

产品联动：整理期间桌宠播"睡觉/整理记忆"动画——**后台任务是剧情的一部分**。

## 5. 存储与检索实现

- SQLite（结构化：标签、时间、状态机字段）+ sqlite-vec（embedding 检索）。单文件、零运维、可导出——不引入图数据库/重型向量库，MVP 规模（万级事件）完全够用。
- 三因子检索评分（斯坦福 Generative Agents 验证的配方）：`score = α·recency + β·importance + γ·relevance`，先标签/SQL 粗筛再向量精排。
- 检索 budget：单次回对话注入的情景记忆条数有上限（如 5 条），防止上下文膨胀拖慢 LLM——这也是"越用越慢"的第二重保险。

## 6. 接口抽象（保持可替换）

记忆引擎藏在稳定接口后（架构文档 §3），语义记忆与工作记忆的实现在主仓库；若未来高级整理/遗忘策略需要闭源或独立迭代，接口不变、实现可替换：

```ts
interface MemoryEngine {
  record(event: EventDraft): Promise<void>;
  recall(query: RecallQuery, budget: number): Promise<MemoryHit[]>;   // 异步
  quickContext(): Promise<string>;        // 语义+工作记忆，回复必用，毫秒级
  consolidate(): Promise<ConsolidationReport>;   // 睡眠整理
  exportAll(): ExportedMemory;            // 永远可导出
}
```

## 7. 参考实现（业界已验证）

- 斯坦福 **Generative Agents**（Smallville）：recency × importance × relevance 三因子记忆流。
- **Letta（MemGPT）**：分层记忆与自编辑记忆。
- **mem0 / Zep(Graphiti)**：抽取-蒸馏式长期记忆、时间感知。
- 我们的差异：**遗忘的三段退化 + 拟人化表达**是以上项目都没有产品化的部分，是体验差异点。

## 8. 隐私承诺

- 记忆数据仅存本机 SQLite；云端 LLM 调用仅携带检索 budget 内的最小上下文。
- 导出 / 一键清空 / 关闭云模型（纯本地 Ollama 档）均为一级设置项。
- 记忆文件格式写入公开规范，第三方工具可直读。
